Bitterless · MCP · local only

Todo 通信机制：不开放端口的 MCP 接入

目标是让其他 agent 应用通过 MCP 增删改查 Bitterless todo，同时不启动 HTTP 服务、不监听 TCP 端口，并继续复用当前 Electron 应用的 SQLite、加密和 UI 刷新机制。

对外协议 MCP stdio，JSON-RPC，经由子进程 stdin/stdout。
本机桥接 Unix domain socket 或 Windows named pipe，不占端口。
数据归属 Bitterless GUI/main 继续持有 SQLite 访问权。
client Agent app

启动桌面端生成的 bitterless-mcp helper。

→
stdio server bitterless-mcp

对外承接 MCP stdio，对内连接本机 bridge。

→
owner process Bitterless GUI

通过本机 pipe 接收请求并调用 todo DAO。

01

核心结论

推荐

同一个安装包，专用 helper 入口

Bitterless 桌面端在 userData 下生成 bin/bitterless-mcp 或 bin/bitterless-mcp.cmd。外部 agent 只配置这个 helper，不直接指向 app bundle。

启动

由 MCP host 启动子进程

其他 agent 应用只配置 command。它们不是连接一个端口，而是拉起 helper 子进程并通过 stdin/stdout 发 JSON-RPC。

边界

stdio 不能直连已运行 GUI

stdio 是父子进程通信，不是 app-to-app socket。要和已运行 Bitterless 通信，需要在本机再做一层 pipe 或 named pipe。

02

运行时链路

Agent app
读取 MCP 配置，启动桌面端弹窗复制出来的 bitterless-mcp helper 路径。
MCP stdio
Agent 通过 stdin/stdout 调用 domain.list、todo.create、todo.update、todo.list、todo.status 等 tools。
bitterless-mcp
校验 schema，然后把请求转发到本机 pipe：macOS/Linux 使用 userData/mcp/bridge.sock，Windows 使用 named pipe。
Bitterless GUI
main 进程接管请求，转给现有 sqliteWindow / TodoDao，并在写操作后广播 todo/data_updated。
Renderer
todo 页面收到更新广播后重新加载数据，保持外部 agent 写入和 UI 一致。

为什么第一版不直接 headless 读 SQLite

当前 SQLite 初始化在 preload 侧，release 模式密码依赖 Electron safeStorage 和 renderer localStorage。让外部 MCP 子进程直接读 DB 会过早碰到密码、迁移、并发锁和 UI 刷新问题。先桥接到已运行的 Bitterless GUI，风险更低。

sock 性能与体积

bridge.sock 只是 userData 下的本机 IPC 入口节点，不是日志、队列或数据库文件。请求体不会写进这个文件，数据走内核 socket 缓冲；文件大小通常为 0 或极小的 socket 节点。todo CRUD 这种低频请求的瓶颈更可能是 SQLite 写入和 UI 刷新，而不是 Unix socket / named pipe。实现层会限制单次本机 RPC 帧最大 8 MiB，避免异常客户端把进程内存撑大；todo.list 默认只返回未归档 domain 下的未完成 todo，不读取已完成历史，避免列表体积膨胀。agent 已知一组 todo ID 时，用 todo.status 批量读取 active / completed / deleted / missing，不需要扫描全部完成记录。多个 agent 会话共享同一个 app-wide sock，不能也不需要按会话创建 sock；每个会话用自己的 lastEventId cursor 区分读取进度。

Domain 与 Focus 规则

MCP 只允许 agent 读取未归档 domain 列表和描述，不允许创建或修改 domain。Agent 创建 todo 前先调用 domain.list，按 domain 描述选择已有 domain；没有合适项时使用人类维护的 Others。Focus 不是独立 domain，而是由重要/星标的未完成 todo 派生出来的优先视图。打星标等于 important=true：只有当前 agent 会话被人类下一步动作卡住时才打星；能延后几天的普通跟进不打星。

轮询，不做通知

人类在 UI 中完成、移动、删除或修改 todo 时，Bitterless 写入 append-only 的 todo_events。Agent 恢复会话或被问到下一步时，用 event.list 按 cursor 查一次；如果正在等待人类完成一个阻塞任务，用 event.wait 做有限时长的长轮询。若 agent 手里已有自己创建或正在跟踪的 todo ID，再调用 todo.status 精确确认这些任务是未完成、已完成、已删除还是不存在。当前设计不依赖 MCP push notification。

03

打包方式

方案 A

推荐：userData helper shim

桌面端通过 XPC 生成稳定 helper 路径。helper 内部才调用 Electron 的 --mcp-helper 模式；外部应用看不到 app bundle 内部路径。

// macOS / Linux
~/Library/Application Support/Bitterless/bin/bitterless-mcp

// Windows
%APPDATA%\Bitterless\bin\bitterless-mcp.cmd
内部实现

Electron 只作为 helper runtime

shim 脚本由正在运行的 Bitterless 写入，使用当前安装位置的 process.execPath。应用迁移位置后，下次打开弹窗会刷新 shim。

#!/bin/sh
exec "$BITTERLESS_EXEC_PATH" --mcp-helper "$@"

不要暴露 app bundle 路径

agent 配置里不写 /Applications/Bitterless.app/Contents/MacOS/Bitterless。统一复制桌面端弹窗提供的 helper command。

04

MCP host 配置

macOS

复制桌面端生成的 helper 路径

{
  "mcpServers": {
    "bitterless": {
      "command": "/Users/<you>/Library/Application Support/Bitterless/bin/bitterless-mcp"
    }
  }
}
Windows

复制桌面端生成的 .cmd 路径

{
  "mcpServers": {
    "bitterless": {
      "command": "C:\\Users\\<you>\\AppData\\Roaming\\Bitterless\\bin\\bitterless-mcp.cmd"
    }
  }
}
05

Tool schema 草案

轮询 tool

event.list

{
  "name": "event.list",
  "inputSchema": {
    "type": "object",
    "properties": {
      "afterEventId": { "type": "integer", "minimum": 0 },
      "limit": { "type": "integer", "minimum": 1, "maximum": 100 }
    }
  }
}
长轮询 tool

event.wait

{
  "name": "event.wait",
  "inputSchema": {
    "type": "object",
    "properties": {
      "afterEventId": { "type": "integer", "minimum": 0 },
      "limit": { "type": "integer", "minimum": 1, "maximum": 100 },
      "timeoutMs": { "type": "integer", "minimum": 1000, "maximum": 30000 }
    }
  }
}
读取 tool

domain.list

{
  "name": "domain.list",
  "inputSchema": {
    "type": "object",
    "properties": {}
  },
  "returns": {
    "note": "Only unarchived domains are returned.",
    "domains": [
      { "id": 1, "title": "Bitterless", "description": "..." }
    ],
    "focus": {
      "title": "Focus",
      "description": "Important/starred active todos appear here.",
      "rule": "Star only live-session human blockers; do not star deferrable follow-ups."
    }
  }
}
写入 tool

todo.create

{
  "name": "todo.create",
  "inputSchema": {
    "type": "object",
    "required": ["domainId", "title"],
    "properties": {
      "domainId": { "type": "integer", "minimum": 1 },
      "title": { "type": "string", "minLength": 1, "maxLength": 200 },
      "dueAt": { "type": ["integer", "null"] },
      "important": {
        "type": "boolean",
        "description": "true only when current agent work is blocked on immediate human action"
      },
      "note": { "type": "string", "maxLength": 10000 }
    }
  }
}
读取 tool

todo.list

{
  "name": "todo.list",
  "inputSchema": {
    "type": "object",
    "properties": {
      "domainId": { "type": "integer", "minimum": 1 }
    }
  },
  "returns": {
    "note": "Only incomplete todos from unarchived domains are returned."
  }
}
状态 tool

todo.status

{
  "name": "todo.status",
  "inputSchema": {
    "type": "object",
    "required": ["ids"],
    "properties": {
      "ids": {
        "type": "array",
        "minItems": 1,
        "maxItems": 100,
        "items": { "type": "integer", "minimum": 1 }
      }
    }
  },
  "returns": {
    "note": "Batch status lookup for known todo IDs.",
    "states": ["active", "completed", "deleted", "missing"]
  }
}

返回值使用 MCP 的 structured content：一份机器可读 JSON，加一段简短 text，方便不同 agent host 同时兼容。Domain 的创建、重命名和描述编辑只在人类 UI 中完成。

07

实现清单

1

新增 helper mode

在 main 入口根据 --mcp-helper 分流，helper 模式只保留 stdio server 和 stderr 日志。

2

新增本机 bridge server

GUI main 进程启动 Unix socket / named pipe，提供内部 JSON-RPC 或轻量 RPC，方法名对齐 todo/domain DAO。

3

注册 MCP tools

以 schema 约束输入，限制写入权限，返回结构化内容，并把错误映射为 MCP tool error。

4

写操作后刷新 UI

GUI 侧完成 create/update/delete/complete 后广播 todo/data_updated，复用现有 renderer subscriber。

5

加权限和审计

默认只读；写入需要 Bitterless 设置或环境变量启用。记录 tool 名称、调用时间和简短 payload 摘要。

08

参考规范

MCP stdio transport 的要点是：server 从 stdin 读取消息、向 stdout 写消息，日志写 stderr；tools 通过 schema 描述输入输出。当前设计按这些约束组织。

规范入口： MCP Transports、 MCP Basic Protocol、 MCP Tools。
